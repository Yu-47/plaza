# 设计文档

本文档按开发阶段记录需求、设计决定和取舍。每个决定都写明：为什么这样做、放弃了哪些做法、付出了什么代价。

---

## 阶段 1：需求与功能决定

### 需求（"什么算对"）

| 编号 | 内容 | 为什么 |
|---|---|---|
| 需求 1 | 同一格被多人修改时，以服务器收到的最后一次为准 | 谁先谁后本来就不确定，最终是红是蓝都可以接受；真正的错误是混色或半红半蓝。因此只需一条明确的规则来定"谁是最后"，这里采用服务器收到请求的顺序 |
| 需求 2 | 快照必须是画布在某一真实时刻的完整画面，但不保证是最新的 | 边读边改会拼出一幅从未存在过的画面。"最新"本身无法保证，因为数据在传输途中画布可能又变了，所以只要求快照"真实存在过" |
| 需求 3 | 印章整体生效，不存在"盖了一半"的状态 | 两个印章逐格交错会产生混杂的颜色，任何先后顺序都解释不了；盖到一半的画面被别人看到，也不符合用户意图 |

**总原则：** 无论多少人同时操作，任何人看到的结果都必须等于"把这些操作按某种顺序一个接一个执行"的结果（可串行化）。

### 功能决定

| 编号 | 决定 | 为什么 | 放弃的做法 / 代价 |
|---|---|---|---|
| 决定 1 | 画布固定大小，尺寸可配置 | 可扩展画布会让"坐标是否合法""快照大小"随时间变化，还会引入扩展瞬间的并发问题，在 10–14 天的时间框内性价比低 | 放弃：可扩展画布（留作加分项）。代价：画布满了无法变大 |
| 决定 2 | 16 色调色板，颜色数可配置 | 每格只需 1 字节，而 RGB 需要 3 字节，快照数据量约为 RGB 的 1/3；输入检查只需判断编号范围；画风统一 | 放弃：任意 RGB。代价：用户可选颜色较少 |
| 决定 3 | 印章为自定义图案，尺寸设上限 | 纯色方块是图案的特例，图案更通用；尺寸上限防止一次覆盖大片画布 | 代价：输入数据更大，需要检查的内容更多 |
| 决定 4 | 印章只要有一格超出画布就整个拒绝；先完成全部检查，再写入 | 超出边缘多半是用户放错了位置，明确报错比悄悄画一部分更符合预期。先检查后写入，可以保证不出现"画了一半"的可见状态，也不需要撤回逻辑 | 放弃：只画画布内的部分（同样满足原子性，但不符合用户意图）；边画边检查、出错再撤回 |
| 决定 5 | 用户连接时报一次用户名；冷却按用户名记录在服务器端 | 永远不信任客户端，所以冷却必须由服务器记录。按用户名记录，断线重连后冷却依然有效，规则对所有人一致 | 放弃：按连接记录（重连即清零）。已知局限：换个名字即可绕过冷却，真正解决需要账号认证，超出本项目范围 |
| 决定 6 | 冷却时长 = 每格冷却时间 × 绘制格数 | 印章越大代价越大，印章就无法用来绕过冷却 | 放弃：每次操作固定冷却。代价：大印章需要等待很久，因此配合尺寸上限使用 |
| 决定 7 | 同名的多个连接视为同一用户，共用冷却 | 重连不受影响；开多条同名连接也无法绕过冷却 | 代价：两个真正不同的人碰巧同名时，会共用同一份冷却 |
| 决定 8 | 画布用一维 `bytearray` 按行优先存储 | 每格 1 字节，正好容纳一个颜色编号，实测内存约为 Python 列表的 1/8；快照只需整体复制一次，结果可直接发送；写入超出 0–255 的值会直接报错 | 放弃：二维列表（浅复制容易踩坑）、字典（生成快照最慢） |
| 决定 9 | 通信采用 WebSocket | 服务器需要主动推送更新，HTTP 请求-响应模式做不到；浏览器无法直接使用 TCP；WebSocket 自带消息边界，无需自己处理粘包 | 放弃：裸 TCP（需自行分帧，浏览器不可用）、HTTP 轮询（大量无效请求）。代价：引入一个第三方库依赖 |
| 决定 10 | 提供一个最简网页前端（显示画布、点击画一格），放在最后实现 | 面试时可以直观演示；后端岗位的重点仍是服务器 | 代价：额外的 HTML/JS 工作量，因此排在最后 |
| 决定 11 | 分层：`Canvas` 不感知网络，网络层只负责"收消息 → 调用 Canvas → 回复" | 更换通信方式时只需修改网络层；`Canvas` 可以脱离网络单独测试 | 代价：多一层代码 |
| 决定 12 | 命令和回复用 JSON，快照用二进制 | JSON 字段有名字，新增字段不会破坏旧格式，Python 和 JS 都自带解析器；二进制快照的数据量约为 JSON 的 1/3，且画布本身就是 `bytearray`，可直接发送 | 代价：客户端要处理两种消息；二进制不可读，调试不便 |
| 决定 13 | 连接后由服务器发送 `welcome`，告知画布尺寸等配置 | 同一信息只保存在一处，由服务器告知客户端，避免两边配置不一致 | 代价：多一轮握手 |
| 决定 14 | 印章图案用二维列表表示；各行长度不一致则整个拒绝 | 一眼能看出图案形状，宽高可直接从列表算出。各行长度不一致时宽度有歧义，按某一行的宽度读取其他行会越界，导致盖到一半出错 | 放弃：宽高加一维列表（宽高与列表长度可能对不上）。代价：需要逐行检查长度 |

## 通信协议

**坐标约定：** x 为列，y 为行，均从 0 开始。
**消息格式：** 命令和回复都是 JSON 文本消息，只有快照是二进制消息。
**共同字段：** 所有 JSON 消息都有 `type` 字段，表示消息种类。

### 0. 连接握手
连接后客户端必须先发送 `hello`，在此之前的其他请求一律返回 `not_identified`。同一条连接上的第二次 `hello` 返回 `already_identified`。

- 请求：`{"type": "hello", "name": "xiaoming"}`
- 成功：`{"type": "welcome", "width": 1000, "height": 1000, "palette_size": 16, "cooldown_ms_per_pixel": 1000, "max_stamp_size": 8}`
  （`cooldown_ms_per_pixel` 和 `max_stamp_size` 在阶段 4 实现后加入）
- 失败：`already_identified`；`invalid_name`（名字为空或过长，待实现）

### 1. 画一格
- 请求：`{"type": "paint", "x": 3, "y": 5, "color": 7}`
- 成功：`{"type": "painted", "x": 3, "y": 5, "color": 7, "cooldown_ms": 1000}`
  （`cooldown_ms` 在阶段 4 实现后加入）
- 失败：`out_of_bounds` / `invalid_color` / `cooldown`

### 2. 读一格
- 请求：`{"type": "read", "x": 3, "y": 5}`
- 成功：`{"type": "pixel", "x": 3, "y": 5, "color": 7}`
- 失败：`out_of_bounds`

### 3. 快照
- 请求：`{"type": "snapshot"}`
- 成功：一条**二进制**消息，共 width × height 个字节，按行优先排列，每个字节是一格的颜色编号。宽高从 `welcome` 消息获得。
- 客户端规则：收到二进制消息即为快照；收到文本消息则按 JSON 解析。

### 4. 盖印章
- 请求：
  ```json
  {"type": "stamp", "x": 10, "y": 20,
   "pattern": [[7, 7, 7],
               [7, 3, 7],
               [7, 7, 7]]}
  ```
  `x`、`y` 是图案左上角的坐标；`pattern` 是二维列表，每个子列表代表一行。
- 成功：`{"type": "stamped", "x": 10, "y": 20, "width": 3, "height": 3, "cooldown_ms": 9000}`
- 失败：`out_of_bounds` / `invalid_color` / `invalid_pattern` / `stamp_too_large` / `cooldown`

### 错误回复（统一格式）
`{"type": "error", "code": "<代号>", "message": "<给人看的说明>", ...附带字段}`

`code` 供程序判断，`message` 供人阅读，两者分开，修改措辞不会影响客户端逻辑。

| 代号 | 含义 | 附带字段 |
|---|---|---|
| `invalid_message` | 不是合法 JSON、缺少字段、多余字段或字段类型不对 | — |
| `unknown_type` | `type` 无法识别 | — |
| `not_identified` | 尚未发送 `hello` | — |
| `already_identified` | 同一连接已经发送过 `hello` | — |
| `invalid_name` | 名字为空或过长（待实现） | — |
| `out_of_bounds` | 坐标超出画布（印章：任一格超出） | — |
| `invalid_color` | 颜色编号不在 0 到 palette_size − 1 之间 | — |
| `invalid_pattern` | 图案为空，或各行长度不一致 | — |
| `stamp_too_large` | 图案宽或高超过上限 | `max_stamp_size` |
| `cooldown` | 冷却中 | `retry_after_ms` |

（订阅相关的消息在阶段 5 设计。）

### 设计决定

| 编号 | 决定 | 为什么 | 放弃的做法 / 代价 |
|---|---|---|---|
| 决定 15 | 同一连接上的第二次 `hello` 一律拒绝，回复 `already_identified`，名字保持不变 | 冷却按名字记录（决定 5）。如果允许改名，用户在冷却期间发一次 `hello` 换个名字，就能立刻继续画，冷却形同虚设 | 放弃：允许改名；同名重发时接受。选择一律拒绝，是因为规则越少例外越不容易出错，正常客户端也只在连接时发送一次 `hello` |
| 决定 16 | `handle_message` 是不涉及网络的普通函数（非 `async`），网络层只负责收发 | ① 可以脱离网络直接测试；② 普通函数内部无法使用 `await`，因此处理一条消息的过程不会被其他连接插入（见阶段 3），Python 的语法本身替我们保证了这一点 | 代价：如果将来需要在处理消息时等待外部资源（例如数据库），必须重新设计，并重新评估原子性 |
| 决定 17 | 画布在 `main` 中只创建一次，由所有连接共享；每条连接各自持有一个 `Session`，记录该连接的身份 | r/place 的核心是所有人共同完成一幅画，因此画布必须共享；而"是否已发送 hello、名字是什么"属于每条连接自己的状态，不应共享 | 放弃：每条连接一块画布。代价：共享状态需要考虑并发访问（见阶段 3） |

### 协议层的分工

**规则：** 协议层负责"格式和类型"，即不需要知道画布任何信息就能判断的问题；`Canvas` 负责"内容是否合法"，即需要知道画布尺寸、调色板大小才能判断的问题。

| # | 收到的消息 | 由谁拦截 |
|---|---|---|
| a | `hello world`（不是 JSON） | 协议层 |
| b | `{"type": "jump"}` | 协议层 |
| c | `{"type": "paint", "x": 3, "y": 5}`（缺少 color） | 协议层 |
| d | `{"type": "paint", "x": "3", "y": 5, "color": 7}` | 协议层 |
| e | `{"type": "paint", "x": 3.0, "y": 5, "color": 7}` | 协议层 |
| f | `{"type": "paint", "x": true, "y": 5, "color": 7}` | 协议层 |
| g | `{"type": "paint", "x": -1, "y": 5, "color": 7}` | Canvas |
| h | `{"type": "paint", "x": 3, "y": 5, "color": 99}` | Canvas |
| i | `{"type": "stamp", "x": 0, "y": 0, "pattern": [[1, 2], [3]]}` | Canvas |
| j | `{"type": "stamp", "x": 0, "y": 0, "pattern": [[1, 2], [3, "k"]]}` | 协议层 |
| k | `{"type": "paint", "x": 3, "y": 5, "color": 7, "z": 1}`（多余字段） | 协议层 |

关于 k（多余字段），选择**严格拒绝**：客户端发来服务器不认识的字段，多半说明客户端写错了，立即报错有助于尽早发现问题。代价是将来协议新增字段时，客户端和服务器需要同步升级。

注意 f：在 Python 中 `bool` 是 `int` 的子类，`isinstance(True, int)` 为真，因此整数检查使用 `type(v) is int`。

### 请求的数据结构

每种请求解析为一个不可变的 `dataclass`。解析完成后，后续代码只读取请求，不应修改它；`frozen=True` 能让任何误改立即报错。

```python
@dataclass(frozen=True)
class HelloRequest:
    name: str

@dataclass(frozen=True)
class ReadRequest:
    x: int
    y: int

@dataclass(frozen=True)
class PaintRequest:
    x: int
    y: int
    color: int

@dataclass(frozen=True)
class StampRequest:
    x: int
    y: int
    pattern: list[list[int]]

@dataclass(frozen=True)
class SnapshotRequest:
    pass
```

请求类不包含 `type` 字段：类名本身已经说明了请求种类，再存一份是重复信息。

## 测试策略

所有模块均采用测试驱动开发：先写测试并确认其失败，再编写实现直至通过。

### 通用测试角度

| 角度 | 示例 |
|---|---|
| 正常情况 | 画一格后读出，颜色是否正确 |
| 边界值 | 坐标 0 和 width − 1 能否绘制；颜色 0 和 palette_size − 1 能否绘制 |
| 越界 | 坐标 −1 和 width；颜色 −1 和 palette_size |
| 构造参数 | width 为 0 或负数 |
| 失败不留痕 | 操作失败后，画布和会话状态保持不变 |
| 独立性 | 两块画布、两个会话互不影响 |

### Canvas（`test_canvas.py`）

**`__init__`**
- 正常创建 3×2 画布：不报错，width = 3，height = 2
- width 或 height 为 0 或负数：`ValueError`
- palette_size 为 1 和 256：正常创建；为 0 和 257：`ValueError`

**`get`**
- 新画布读取 (0, 0) 和右下角 (width − 1, height − 1)：结果为 0
- 四个方向各越界一格，即 (−1, 0)、(0, −1)、(width, 0)、(0, height)：`OutOfBoundsError`

**`paint`**
- 画 (1, 1) 颜色 5 后读取，结果为 5
- 颜色 0 和 palette_size − 1 可以绘制；−1 和 palette_size 抛出 `InvalidColorError`，且原格颜色不变
- 坐标四个方向越界：`OutOfBoundsError`
- 画一格不影响其他格
- 同一格画两次，以后一次为准（需求 1）

**`snapshot`**
- 返回类型为 `bytes`，长度为 width × height
- 新画布的快照全为 0
- 在 3×2 画布上画 (x = 2, y = 1) 颜色 7，快照应为 `[0, 0, 0, 0, 0, 7]`（验证行优先，确认行列未颠倒）
- 获取快照后再绘制，之前的快照内容不变（需求 2）

**`stamp`**
- 使用非对称、非正方形的图案（如 `[[1, 2], [3, 4]]`、1×3、3×1），确认每格位置正确，可发现行列颠倒
- 图案恰好贴住右下角边缘时可以盖上
- 只有一格超出边缘：`OutOfBoundsError`
- 只有一格颜色非法：`InvalidColorError`
- 空图案 `[]`、空行 `[[]]`、各行长度不一致：`InvalidPatternError`
- 以上任一失败发生后，通过比较整张快照，确认画布一格都没有变化

### 协议层（`test_protocol.py`）

- **合法请求**：五种请求各自解析为正确的对象
- **应当放行（交由 Canvas 判断）**：负坐标、超出调色板的颜色、各行不等长的图案
- **`invalid_message`**
  - 不是 JSON：`hello world`、空字符串
  - 合法 JSON 但不是对象：`[1, 2]`、`"hello"`、`5`、`null`
  - `type` 缺失，或不是字符串
  - 字段缺少或多余（包括 `snapshot` 带多余字段）
  - 字段类型错误：字符串 `"3"`、小数 `3.0`、布尔 `true`、`null`；`name` 为数字
  - `pattern` 类型错误：不是列表、某行不是列表、元素是字符串或布尔
- **`unknown_type`**：`{"type": "jump"}`、`{"type": "PAINT"}`（区分大小写）
- 每个失败用例都检查 `code`，而不仅仅检查是否抛出异常

**经验：** 测试文本中必须使用 JSON 写法（`true`、`null`），而不是 Python 写法（`True`、`None`）。否则用例会在 JSON 解析阶段就失败，测试虽然通过，测的却不是想测的内容。通过"故意弄坏实现、确认测试会失败"的方法发现了这一问题。

## 阶段 3：多用户并发

### 分析

- **哪些操作有并发风险：** "读-改-写"类操作，即写入的内容依赖于先前读到的值（例如计数器加一、冷却检查）。如果读和写之间被其他任务插入，就会出现丢失更新。`paint` 写入的是绝对值，不依赖读取结果，多人同时绘制时以最后一次为准，符合需求 1。
- **asyncio 的切换点：** asyncio 采用协作式调度，只会在 `await` 处切换任务。两个 `await` 之间的代码，对其他协程而言是不可分割的整体。
- **对本服务器的意义：** `handler` 中的 `await` 只出现在接收消息之前和发送回复之后，而 `handle_message` 是普通函数，内部没有 `await`。因此处理每条消息的完整过程，包括读取冷却记录、检查、写入画布、更新冷却记录，对其他连接而言都是原子的，无需加锁即可满足需求 2 和需求 3。

### 设计决定

| 编号 | 决定 | 为什么 | 放弃的做法 / 代价 |
|---|---|---|---|
| 决定 18 | 并发模型采用 asyncio，而非多线程 | ① 线程无法提速：CPython 有 GIL，同一时刻只有一个线程执行 Python 代码，而服务器的时间主要花在等待网络上；② 线程更难写对：线程由操作系统抢占式调度，可能在任意位置被切换，`Canvas` 的所有方法都需要加锁，遗漏任何一处都会产生难以复现的偶发错误；③ asyncio 只在 `await` 处切换，配合决定 16，处理每条消息天然是原子的 | 放弃：每条连接一个线程。代价：协程中不能调用阻塞操作，否则会卡住所有连接；关键路径上一旦引入 `await`，就需要重新评估原子性并考虑使用 `asyncio.Lock` |

### 验证

- **并发测试（`test_concurrency.py`）：** 启动真实服务器，两个客户端同时在同一 4×4 区域反复盖纯色印章（颜色分别为 1 和 4），第三个客户端不断获取快照。断言每张快照中该区域的颜色完全一致，从不混杂；结束后再断言该区域全为 1 或全为 4，以排除"印章全部失败、区域一直为 0"导致的假通过。
- **证明测试有效：** 临时编写一个"坏服务器"，在印章逐格绘制的过程中执行 `await asyncio.sleep(0)`。测试在第一次盖章时即发现交错（区域为 `[4, 4, 0, 0, …]`）。删除这行 `await` 后，即使仍是逐格绘制，测试也能通过。这证明了 asyncio 中的原子性取决于中间是否存在 `await`，而不是操作是否"一步完成"。

### 设计决定

| 编号 | 决定 | 为什么 | 放弃的做法 / 代价 |
|---|---|---|---|
| 决定 19 | 先检查冷却，再交给 `Canvas` 同时完成合法性检查和写入；只有成功后才扣除冷却，失败不扣 | `Canvas` 的接口无需修改，`paint` 和 `stamp` 照常同时完成检查与写入，代码更简单。由于失败不扣冷却，两种检查顺序下用户的总等待时间相同，区别只在于先看到哪个错误 | 放弃：先检查合法性（需要为 `Canvas` 额外拆出只检查、不写入的方法）。代价：用户在冷却期间发送了写错的请求，要等冷却结束才会发现 |
| 决定 20 | 冷却记录由所有连接共享，按名字记录"最早可再次绘制的时间"，封装在 `rules.py` 的 `Cooldowns` 类中 | 记录在每条连接的 `Session` 里，会导致重连后冷却清零，也无法实现同名共用（违反决定 5、7）。记录"最早可绘制时间"而非"上次绘制时间"，检查时只需比较一次，无需关心上次画了多少格。冷却属于游戏规则，与画布本身无关，因此不放在 `canvas.py` | 代价：需要像画布一样，从 `main` 传入各个连接 |
| 决定 21 | 计时使用 `time.monotonic()`，而非 `time.time()` | 冷却要衡量的是"过了多久"。`time.time()` 可能因系统校时而前后跳变，往回跳会让用户被多锁一段时间，往前跳会让用户提前绘制；`monotonic()` 只会向前走 | 代价：`monotonic()` 的数值不代表现实时刻，不能直接展示给用户 |
| 决定 22 | `Cooldowns` 不自行读取时间，由调用方通过参数 `now` 传入（依赖注入） | 测试可以直接传入任意时间，无需真实等待，测试瞬间完成；正式运行时由网络层每收到一条消息读取一次时钟 | 代价：调用方每次都要多传一个参数 |
